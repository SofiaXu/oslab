# 实验二：让多个进程安全地取走同一批数据

> 完整仓库包含独立参考实现；学生发布包不含 `reference/`。学生包中跳过参考演示，完成代码后使用默认的 `make check-lab2` 验收自己的实现。

本实验在 **Ubuntu 宿主机**运行。WSL2 中的 Ubuntu 终端也是这里的宿主环境，不是 Linux 0.11 来宾系统。你需要会写 C 的循环、结构体和函数；不需要汇编基础。建议先完成本实验，再学习内核中的信号量实现。

完成后，你应该能解释：不同进程如何共享数据、为什么要同时使用计数信号量和互斥信号量、为什么数字取对了但打印顺序仍可能出错，以及异常退出时如何避免其他进程永远等待。

## 1. 任务与可观察结果

创建一个父进程负责管理，再由它 `fork()` 出 **一个生产者进程、N 个消费者进程（N>1）**。生产者依次生产 `0..M`，两端都包含，默认 `M=500`，所以共有 **501 个数**。文件支持的共享环形缓冲区最多容纳 10 个数。消费者每次取走一个数，向标准输出写一行：

```text
21901:0
21902:1
21901:2
```

左边是实际消费者 PID，右边必须从 0 到 M 严格递增，每个数字恰好出现一次。不同运行的 PID 和消费者分工可以变化。文件名、信号量名和错误信息写入标准错误，不混进数据输出。

参考程序不使用线程。链接命令中的 `-pthread` 是 POSIX 支持选项，不表示调用了 `pthread_create()`。

| --- | --- |

## 3. 从普通文件到共享环形队列

`fork()` 后，普通全局变量并不能让父子进程相互看到修改。文件存在也不意味着 `fread()` 的用户态缓存能自动共享。本实验采用下面的路径：

1. `open(O_CREAT|O_EXCL)` 或 `mkstemp()` 创建文件。
2. `ftruncate()` 把文件大小设为共享结构体大小。
3. `mmap(..., MAP_SHARED, fd, 0)` 把它映射到内存，再 `fork()`。
4. 所有子进程使用继承的映射读写同一文件支持的内存。

队列保存 `slots[10]`、读下标 `head`、写下标 `tail`，以及用于检查容量的 `count`。下标更新为 `(下标+1)%10`。例如 `tail=9` 写入最后一个格子后回到 0；这不代表缓冲区变空。空满关系必须另外管理。`count` 只在互斥区内更新，并检查 `0 <= count <= 10`。

这是宿主机的文件映射共享方案；不要求学生在 Linux 0.11 中实现 `mmap()`，也不能把它原样复制到旧内核。

## 4. 三个信号量各解决什么问题

通过 `sem_open()` 创建有名字的 POSIX 信号量，并检查 `SEM_FAILED`：

| 信号量 | 初值 | 表示什么 |
| --- | ---: | --- |
| `empty` | 10 | 还能写入多少个数 |
| `full` | 0 | 还能取走多少个数 |
| `mutex` | 1 | 当前是否有人修改队列或打印结果 |

`sem_wait()`，也叫 P 操作：有额度时减一，没有时等待。`sem_post()`，也叫 V 操作：增加一个额度，并可能唤醒等待者。

```text
生产者：P(empty) → P(mutex) → 写入并更新队列 → V(mutex) → V(full)
消费者：P(full)  → P(mutex) → 取出、更新队列、打印 → V(mutex) → V(empty)
```

**打印必须放在取数的同一个互斥区中。** 如果 A 取到 0 后先解锁，B 可能取到 1 并先打印，数字没有重复，输出却不符合题目要求。

不要先锁 `mutex` 再等 `full`：缓冲区为空时，消费者可能拿着锁睡觉，生产者又要拿同一把锁才能放入数据，形成死锁。

参考程序为每个消费者分配固定次数：总数 `T=M+1`，第 `i` 个消费者取 `T/N + (i < T%N)` 次（这里 i 从 0 开始）。这些次数之和恰好为 T；谁先取得信号量由调度决定。这样既不需要在共享变量中无锁猜测何时结束，也不需要用特殊数字充当结束标记。

## 6. 收尾与失败处理也是实验内容

父进程保存所有子进程 PID，通过 `waitpid()` 观察退出状态。参考实现使用非阻塞轮询，间隔约 10 ms，避免“检查退出标志后、进入阻塞等待前刚好收到信号”的竞态。

- `SIGINT`（Ctrl+C）、`SIGTERM`、`SIGHUP` 的处理函数只记录 `sig_atomic_t` 标志，不在处理函数中调用 `printf()`、释放内存或删除资源。
- `sem_wait()` 因 `EINTR` 返回时，先判断是否正在取消；普通中断可以重试，退出请求必须使当前工作失败返回。
- 一旦子进程异常退出，父进程终止其他子进程并逐个回收。不能指望其他进程继续拿到死者持有的 `mutex`；POSIX 信号量不是自动恢复的健壮互斥锁。
- 每个子进程关闭自己继承的信号量句柄、映射和文件描述符。父进程负责 `sem_close()`、`sem_unlink()`、`munmap()`、`close()` 和删除共享文件。`sem_close()` 与 `sem_unlink()` 不是同一件事。

参考版取消时使用 `SIGKILL` 终止同组工作子进程，即使它们被暂停也能回收。**不要对父进程使用 `kill -9` 来测试自动清理**：SIGKILL 无法被捕获，父进程死亡时没有机会执行清理；这也不是本实验承诺的故障恢复范围。需要手工排查时，根据标准错误中本次运行的 `RESOURCES` 行，核对文件及 `/dev/shm/sem.oslab_pc_*`；只清理已经结束的本次实验资源。

对照实验：

```bash
./build/lab02/reference/pc --consumers 8 --max 2000 > /tmp/pc-safe.txt
./build/lab02/reference/pc --consumers 8 --max 2000 --unsafe > /tmp/pc-unsafe.txt
python3 - <<'PY'
from pathlib import Path
for name in ('safe', 'unsafe'):
    values = [int(x.split(':')[1]) for x in Path('/tmp/pc-' + name + '.txt').read_text().splitlines()]
    print(name, '严格递增且恰好一次:', values == list(range(2001)))
PY
```

`--unsafe` 去掉 `mutex`，保留 `empty/full`。它会刻意扩大读下标更新的竞争窗口，常见现象是重复、遗漏、乱序，但**不能断言某次运行必然出错**。这个模式刻意含有数据竞争，不能当作正确实现。保留空满计数和固定消费次数，使对照实验通常能够结束；它不等同于“删除全部信号量”。

原材料要求思考删除所有信号量后的行为：请另做本地变体，设置外部超时，观察覆盖尚未读取的数据、读取空槽、结束判断失效等现象。不要把全部删除版本作为正常验收程序。

原材料图片中的“另一种设计”转写如下，供不依赖 Word 图片的讨论：

```text
Producer: 生成 item → P(empty) → P(mutex) → 放入缓冲区 → V(mutex) → V(full)
Consumer: P(full) → P(mutex) → 取出 item → V(mutex) → 消费 item → V(empty)
```

请区分“消费 item”与“从缓冲区取走 item”。上述方案对共享队列是否安全？把 `V(empty)` 提前到消费之前，对并行性有什么影响？若“消费”是本实验的打印，能否满足输出严格递增？另外用“先拿 mutex 再等 full”的具体例子分析死锁，比较两者不能只看是否都调用了三种信号量。
